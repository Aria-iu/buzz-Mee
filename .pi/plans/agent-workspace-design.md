# `.pi` Agent 工作区设计

## 目标

在 Buzz fork 中建立一个与上游源代码明确隔离的 Agent 工作区，用于保存项目理解、设计决策、开发计划、测试结果和变更摘要。第一阶段仅开展只读调研，不修改任何原项目文件。

## 边界

- 所有 Agent 过程记录只能写入仓库根目录下的 `.pi/`。
- 项目源代码、现有配置、现有文档和现有测试在调研阶段保持不变。
- 调研文档使用中文，代码符号、文件路径、协议名和必要技术术语保留英文。
- 未经项目所有者明确要求，不执行 `git commit` 或远程推送。
- 原始命令输出、临时草稿、会话流水和可能包含敏感信息的内容只能进入 `.pi/local/`。

## 目录结构

```text
.pi/
├── .gitignore
├── README.md
├── INDEX.md
├── knowledge/
│   ├── project-overview.md
│   ├── architecture.md
│   ├── module-map.md
│   ├── core-workflows.md
│   ├── terminology.md
│   ├── setup-and-testing.md
│   └── extension-points.md
├── decisions/
├── plans/
├── reports/
└── local/
```

## 目录职责

- `knowledge/`：经过整理、可以复核的项目知识。每项重要结论应指向仓库文件路径。
- `decisions/`：后续开发中的架构决策记录；调研阶段不预先制造决策。
- `plans/`：经确认的调研或开发计划，以及本设计文档。
- `reports/`：阶段总结、变更摘要、测试结果和风险报告。
- `local/`：原始日志、临时输出和中间产物；默认被 Git 忽略。

## 记录规则

1. 区分“文档明确说明”“代码当前实现”和“Agent 推断”。
2. 重要事实至少引用一个仓库内路径；涉及产品意图时优先引用 `VISION.md` 或相关 `VISION_*.md`。
3. 不把密钥、令牌、个人身份信息、完整环境变量或数据库内容写入可跟踪文档。
4. 只记录有助于理解、决策和验证的内容，不保存逐命令流水账。
5. 文档发现冲突时同时记录两边证据，不擅自选择实现或愿景作为唯一真相。
6. 每次更新同步维护 `.pi/INDEX.md`，让读者可以从一个入口了解当前进度。

## 调研流程

1. 建立项目概览和产品边界。
2. 绘制仓库模块地图及依赖关系。
3. 追踪核心业务流程和关键数据边界。
4. 整理环境搭建、构建与测试方式，但不在只读阶段启动破坏性服务。
5. 识别适合个人扩展的接口、耦合点和风险。
6. 输出阶段报告，由项目所有者决定是否进入开发阶段。

## 后续开发原则

进入开发阶段后，新功能代码仍应放入 Buzz 既有架构所要求的模块，而不是放入 `.pi/`。`.pi/` 只保存 Agent 工作记录。通过独立分支和清晰 Git 历史区分上游代码与个人改动；物理目录隔离不能替代正确的模块边界。

## 验收标准

- Agent 生成的记录均位于 `.pi/`。
- `.pi/local/` 内容不会被 Git 跟踪。
- 第一阶段没有原项目文件被修改。
- 项目理解文档具有路径证据、清晰状态和统一导航。
- 未收到明确指令时不存在 Agent 创建的 Git commit 或远程推送。
